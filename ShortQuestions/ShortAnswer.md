1. Three Pillars of Observability
The three pillars of observability are metrics, logs, and traces. Metrics are numerical measurements collected over time, such as CPU usage, request count, error rate, or latency, and their main purpose is to show the overall health and trend of a system. Logs are detailed event records produced by applications and infrastructure, and their main purpose is to provide exact context about what happened at a specific moment, such as an exception message or user action. Traces show the full path of a request as it moves across multiple services, and their main purpose is to help engineers understand where time was spent and where failures occurred in a distributed system. Together, metrics tell you that there is a problem, logs tell you what happened, and traces tell you where it happened.

2. Metrics Data Types
The four common metric types are counter, gauge, histogram, and summary. A counter only goes up, so it is used for things like total HTTP requests or total failed logins. A gauge can go up or down, so it is useful for values such as memory usage, queue length, or number of active connections. A histogram records observations into buckets, so it is commonly used for request latency, because it helps show how many requests finished within certain time ranges like 100 ms or 500 ms. A summary also measures observed values such as latency, but it focuses on quantiles like p50 or p95 directly. For example, a team might use a counter for total API calls, a gauge for CPU usage, a histogram for request duration buckets, and a summary for tracking response-time percentiles.

3. Structured Logging
Structured logging means logs are written in a consistent machine-readable format, usually as key-value pairs or JSON, instead of free-form plain text. For example, instead of writing “payment failed for user 123,” a structured log may contain fields like event=payment_failed, user_id=123, order_id=456, and error_code=timeout. It is preferred in production because it is much easier to search, filter, aggregate, and analyze. Structured logs also work much better with log platforms such as ELK or Splunk, because engineers can query specific fields instead of guessing text patterns. In short, structured logging makes logs more reliable for automation, monitoring, debugging, and incident investigation.

4. Distributed Tracing Concepts
A trace represents the complete journey of one request through a distributed system. A span is one individual unit of work inside that trace, such as one database call, one HTTP call, or one function execution. A trace is made up of multiple spans linked together. Context propagation is the mechanism that passes tracing information, such as trace ID and span ID, from one service to another, usually through request headers. This is what allows all spans from different services to be connected into one trace. So the relationship is: a trace is the full story, spans are the individual steps, and context propagation is what keeps all those steps connected across service boundaries.

5. Prometheus Pull Model
In the Prometheus pull model, Prometheus periodically sends requests to application metric endpoints, usually something like /metrics, and collects the latest metric values from those targets. This means the monitoring system is responsible for scraping the data instead of the application pushing it out. One major advantage is that Prometheus controls the collection schedule, target discovery, and retry behavior, which makes monitoring simpler and more centralized. It is also easy to check whether a target is up, because if Prometheus cannot scrape it, that itself is useful information. Another advantage is that applications do not need extra logic to push data somewhere. However, the pull model also has disadvantages. It works best when Prometheus can reach the target directly, so it can be harder in environments where services are short-lived, isolated, or behind strict network boundaries. Compared with a push model, it is less natural for one-time batch jobs, because those jobs may finish before Prometheus gets a chance to scrape them. In contrast, a push model can be more convenient for short-lived jobs, but it is usually harder to manage centrally and may lose the direct health-check benefit that pull provides.
